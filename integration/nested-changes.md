# Вложенные данные и paths

У сотрудника может быть несколько личных карточек, у каждой карточки — свои периоды нетрудоспособности. Изменение одного периода должно дойти до наблюдателя, попасть в запрос нужной карточки и оставить остальные несохранённые правки на месте.

## Явный журнал и декларативные пути

В [REST-варианте Demo-company](/integration/rest) форма передаёт журнал контактов самостоятельно:

```js
const res = await this.$.aSave.execute({
  employee: this.employee,
  contacts: this.contacts._mutations
});
```

`/employee/save` получает объект `contacts` с массивами `add`, `upd`, `del`, `touch`. В обработчике есть явный обход `add/upd/del` и вызовы соответствующих broker-команд.

Для [вложенных операций `serverEndpoints`](/integration/server-endpoints) используй `paths`: действие само преобразует журналы в строки с `$action`, по которым сервер выбирает `@add`, `@upd` и `@del`.

```html
<pl-action id="aSave" args="[[_compose('...;contacts', employee, contacts)]]"
  paths="contacts"></pl-action>
```

```js
await this.$.aSave.execute();
```

Здесь поля сотрудника развёрнуты в корень `args`, а контакты остаются вложенным массивом. Это соответствует схеме FSE с корневым `@main` и веткой `contacts`. В примере [серверных операций](/integration/server-endpoints) приведена её полная конфигурация.

| | Явный журнал | `paths` |
| --- | --- | --- |
| Аргумент формы | `contacts: contacts._mutations` | `contacts: contacts` |
| JSON контактов | `{ add, upd, del, touch }` | Массив строк с `$action` |
| Откуда берутся изменения | Из `pl-data-observer` | Из того же наблюдателя |
| Серверная обработка | Явный обход в REST-обработчике | Ветки `@add/@upd/@del` в `serverEndpoints` |

Эти форматы не взаимозаменяемы без изменения серверной части. `paths` также можно использовать с отдельным REST endpoint-ом, если тот принимает массивы с `$action`.

## Пути нескольких уровней

Путь отсчитывается от объекта `args`. Для одного объекта карточки с вложенными периодами:

```html
<pl-action id="aSaveCard" endpoint="[[cardSaveEndpoint]]"
  paths="card.inoperabilities"></pl-action>
```

```js
await this.$.aSaveCard.execute({
  employeeId: this.employeeId,
  card: this.card
});
```

Скалярные поля `card` сохраняются в запросе, а `card.inoperabilities` превращается в массив изменённых периодов. Если внутри него не было правок, в запрос уйдёт пустой массив.

Для коллекции карточек с такими же вложенными массивами:

```html
<pl-action id="aSaveCards" endpoint="[[cardsSaveEndpoint]]"
  args="[[_compose('employeeId;cards', employeeId, cards)]]"
  paths="cards,cards.inoperabilities"></pl-action>
```

Указывай пути через запятую **без пробелов**. Индексы `0`, `1` и `*` не нужны: `cards.inoperabilities` применяется к вложенному массиву каждой отправляемой карточки. Путь `cards` ограничивает верхний массив изменёнными строками, второй путь — их дочерние массивы.

`paths` не является списком разрешённых полей. Свойства вне выбранных путей остаются в запросе. Если передать `employee` вместе с `cards`, он тоже будет отправлен. Чтобы сохранить только карточку, передай именно её и необходимые идентификаторы.

Перед сериализацией `pl-action` клонирует аргументы и удаляет служебные ключи с префиксом `_`, включая `_old` и `_mutations`. Поле `$action` сохраняется. Не называй прикладные поля с начального `_`, если они должны пройти через такую очистку.

### Создать карточку вместе с периодом

Добавляй строки через уведомления на каждом уровне. `cardFields` и `periodFields` в примере содержат заполненные поля новых записей:

```js
addCardWithPeriod(cardFields, periodFields) {
  this.push('cards', { ...cardFields, inoperabilities: [] });
  const index = this.cards.length - 1;
  this.push(`cards.${index}.inoperabilities`, periodFields);
}
```

Так оба массива получают записи `add`. Если вложить готовый массив периодов в новый объект без уведомлений по этому массиву, у него может не оказаться `_mutations`. Выбранный в `paths` массив без журнала превращается в пустой массив, даже если в нём есть данные.

## Что означает `touch`

Допустим, наблюдатель подключён ко всему массиву `cards`. Измени описание существующего периода:

```js
this.set('cards.0.inoperabilities.0.other_type_description', 'Уточнённая причина');
```

Сам период попадает в `cards[0].inoperabilities._mutations.upd`. Родительская карточка попадает в `cards._mutations.touch`: её собственные поля не менялись, но через неё нужно передать изменение ниже по дереву.

При `paths="cards,cards.inoperabilities"` сокращённый результат выглядит так:

```json
{
  "args": {
    "employeeId": "101",
    "cards": [{
      "id": "301",
      "$action": "touch",
      "inoperabilities": [{
        "id": "401",
        "other_type_description": "Уточнённая причина",
        "$action": "upd"
      }]
    }]
  }
}
```

`touch` сохраняет путь к дочерним данным. В FSE обход вложенных путей продолжается независимо от того, сработала ли операция родительской строки. Отдельный REST-обработчик должен предусмотреть такой обход сам. Полная схема с передачей `employee_id` и `card_id` — в [serverEndpoints](/integration/server-endpoints).

### Смешанные правки одной карточки

В `pl-data-observer` есть особенность: если сначала изменить вложенный период, а затем собственное поле существующей карточки, карточка может остаться одновременно в `cards._mutations.touch` и `cards._mutations.upd`. `paths` отправит её дважды, и вложенные операции FSE тоже могут выполниться дважды.

Для редактора со смешанными правками используй отдельный наблюдатель на объект карточки и передавай `paths="card.inoperabilities"`. Верхний массив карточек в этом запросе не преобразуется в журнал. Такой вариант реализован ниже. При пакетном сохранении всего дерева потребуется отдельно устранить повторные операции до отправки; сам `paths` этого не делает.

## Сохранить одну личную карточку

Когда карточки сохраняются по одной, вынеси команду и наблюдатель внутрь редактора карточки. Родитель передаёт каждой субформе или компоненту собственный объект `card` и получает `changed` через биндинг.

Измени причины в **обеих** карточках ниже. Сохрани первую: её флаг сбросится, вторая останется изменённой. Добавь период и посмотри запрос — новый период отправляется с `$action: "add"`, после ответа получает идентификатор.

Это учебное расширение модели из `level3/employee/cards.js`. Операции чтения и сохранения карточек обрабатываются локально в памяти страницы; в существующем Demo-company таких HTTP-маршрутов нет. Контракт сохранения примера: `{ employeeId, card }`, ответ — `{ data: { card } }` с полной сохранённой карточкой. Ограничения базы данных этот сервис не воспроизводит.

У родителя нет наблюдателя над общим массивом этих карточек: он объединяет только признаки дочерних редакторов. Наблюдатели дочерних компонентов не пересекаются по данным. После успеха редактор заменяет **свою** `card` ответом сервиса и делает снимок только её.

## Уведомления и контекст строки

Если обе коллекции редактируются в одном шаблоне, у обоих повторов нужна двусторонняя связь:

```html
<template d:repeat="{{cards}}" d:as="card">
  <template d:repeat="{{card.inoperabilities}}" d:as="period">
    <pl-input value="{{period.other_type_description}}"></pl-input>
    <pl-button label="Удалить период" on-click="[[removePeriod]]"></pl-button>
  </template>
</template>
```

```js
removePeriod(event) {
  const { card, period } = event.model;
  const cardIndex = this.cards.indexOf(card);
  this.splice(`cards.${cardIndex}.inoperabilities`, card.inoperabilities.indexOf(period), 1);
}
```

`event.model` содержит оба alias. Поиск родителя через DOM и `data-*` для этого не нужен.

## После успеха и после ошибки

Если одна команда сохраняет всё дерево, примени весь подтверждённый ответ и сделай снимок корня. Если сохраняется одна карточка, работай только с её наблюдателем. Не вызывай `snapshot(cards[0])` у общего наблюдателя, пока в соседних карточках остались правки: общий `isChanged` будет сброшен.

При ошибке сохраняй модель и журналы. На время запроса блокируй поля отправленной карточки, чтобы последующий снимок не принял ввод, который не попал в запрос. Если backend допускает частичный успех одной команды, его ответ должен явно перечислять принятые и отклонённые части; для них нужны соответствующие независимые границы состояния.
