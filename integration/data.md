# Данные формы на примере Demo-company

Карточка сотрудника объединяет персональные данные, контакты и личные карточки с периодами нетрудоспособности. На этом примере удобно проследить весь путь: загрузить модель, передать её в субформы, собрать изменения и сохранить нужную часть.

## Как связаны компоненты

| Задача | Компонент | Что получает форма |
| --- | --- | --- |
| Прочитать список сотрудников или контактов | [`pl-dataset`](/integration/datasets) | Коллекцию `ControlledArray` |
| Получить одну запись или выполнить команду | [`pl-action`](/integration/actions) | `data` из ответа операции |
| Получить права для интерфейса | [`pl-access`](/integration/access) | Объект прав, ролей или опций |
| Определить, что пользователь изменил | [`pl-data-observer`](/integration/change-tracking) | `isChanged` и журналы мутаций |
| Проверить заполнение полей | [`pl-valid-observer`](/integration/validation) | Общий `invalid` своего контейнера |

Модель принадлежит форме. Поля и субформы меняют её через биндинги, наблюдатель отмечает изменения, действие передаёт согласованные аргументы backend-операции. После успеха форма применяет ответ и принимает сохранённую часть за новое исходное состояние.

## Уровни Demo-company

| Уровень | Файлы в `modules/demo-company/forms` | Приём |
| --- | --- | --- |
| Список и простая карточка | `level1/employee_list.js`, `level1/employee_add.js` | Dataset для списка, action для чтения, создания и изменения сотрудника |
| Сотрудник с контактами | `level2/employee_add.js` | Два наблюдателя: объект `employee` и массив `contacts`; передача `contacts._mutations` |
| Экран из субформ | `level3/employee/main.js`, `general.js`, `contacts.js`, `cards.js` | Двусторонние связи между родителем и редакторами; вложенный массив `cards[].inoperabilities` |

Маршруты зарегистрированы в `modules/demo-company/nf-module.js`, обработчики находятся в `lib/employees.js`. Действующий `/employee/save` принимает `employee` и журнал `contacts`, возвращает `{ data: { id } }`. Вложенные `cards` этот обработчик не сохраняет.

## REST или serverEndpoints

В [REST-подходе](/integration/rest) модуль регистрирует маршрут через `web.on`, обработчик явно читает `context.body.args`, управляет транзакцией и вызывает broker. Так реализован текущий Demo-company.

В [serverEndpoints](/integration/server-endpoints) форма описывает серверные операции декларативно: `@main` для основной записи, вложенные `@add/@upd/@del` для дочерних строк. `out` передаёт полученный идентификатор следующим операциям. NFJS публикует FSE-маршрут по имени формы и `id` компонента.

Оба варианта используют `pl-action`. Различаются место описания операции и формат согласованного запроса.

## Два способа передать изменения

**Явный журнал** подходит endpoint-у, который принимает отдельные массивы `add`, `upd`, `del`. Так устроен Demo-company:

```js
const res = await this.$.aSave.execute({
  employee: this.employee,
  contacts: this.contacts._mutations
});
```

**Декларативный `paths`** преобразует выбранные массивы внутри `args` в строки с `$action`. Форма передаёт сами данные; `pl-action` читает их журналы перед сериализацией:

```html
<pl-action id="aSaveDelta" endpoint="[[deltaEndpoint]]"
  args="[[_compose('employee;contacts', employee, contacts)]]"
  paths="contacts"></pl-action>
```

```js
await this.$.aSaveDelta.execute();
```

`deltaEndpoint` — свойство с адресом операции, принимающей строки с `$action`. Форматы этих двух способов различаются. Подробное сравнение и вложенные пути — в главе [«Вложенные данные и `paths`»](/integration/nested-changes).

## Как выбрать границу сохранения

| Сценарий | Организация состояния |
| --- | --- |
| Сотрудник и контакты сохраняются одной транзакцией | Два наблюдателя, одна команда; принять оба снимка после общего успеха |
| Персональные данные и контакты сохраняются независимо | Своя команда и свой наблюдатель на каждую часть |
| Каждая личная карточка сохраняется отдельно | Редактор карточки владеет её наблюдателем и `pl-action`, родитель собирает `changed` |
| Изменения нескольких уровней передаются одной командой | Один наблюдатель на весь сохраняемый граф; `paths` описывает массивы каждого уровня |

Разбор с работающими редакторами: [сохранение части формы](/integration/partial-save), [вложенные карточки и периоды](/integration/nested-changes).

## Запросы и обновление состояния

Чтение запускает обработчик или observer входных параметров: идентификатора, диапазона, страницы. Изменение результата запроса не должно повторять этот же запрос.

**Правильно: загрузка зависит от выбранного сотрудника**

```js
static observers = ['loadEmployee(employeeId)'];
```

**Неправильно: загрузка зависит от собственного результата**

```js
static observers = ['loadEmployee(employeeId, employee, loading)'];
```

Для независимых зон экрана храни свои признаки загрузки и ошибки. Применяй ответ только к той записи, для которой он был запрошен. Не перечитывай редактируемую коллекцию после сохранения соседней части: это затрёт её несохранённые значения.
