# Изменения и снимки данных

`pl-data-observer` связывает редактирование формы с сохранением. Он сравнивает поля с исходным снимком и ведёт журнал операций над массивами. Отправка запроса, откат значений и принятие ответа остаются обязанностями формы.

## Объект и коллекция

У сотрудника персональные данные — один объект, а контакты — массив объектов. В Demo-company они подключены к разным наблюдателям:

```html
<pl-data-observer id="obEmployee" data="{{employee}}"
  is-changed="{{isEmployeeChanged}}"></pl-data-observer>
<pl-data-observer id="obContacts" data="{{contacts}}"
  is-changed="{{isContactsChanged}}"></pl-data-observer>
```

После первоначальной загрузки создай снимки. Здесь обе части нужны для открытия редактора, поэтому их чтение объединено:

```js
async loadEditor() {
  await Promise.all([
    this.$.aGet.execute(),
    this.$.dsContacts.execute()
  ]);
  this.$.obEmployee.snapshot();
  this.$.obContacts.snapshot();
}
```

`aGet.data` связан с `employee`, а `dsContacts.data` — с `contacts`. Снимок создаётся после завершения чтения. Пустую модель нового сотрудника можно принять за исходную сразу после инициализации.

## Что попадает в журнал

Объекты получают служебное поле `_old`, массивы — `_mutations`:

| Поле | Содержимое |
| --- | --- |
| `add` | Новые элементы массива |
| `upd` | Изменённые существующие строки ближайшей к правке коллекции |
| `del` | Удалённые существующие элементы |
| `touch` | Родительские строки, затронутые изменением вложенной коллекции или её элементов |

У отдельного корневого объекта `employee` нет массива `employee._mutations`. Наблюдатель сравнивает его поля с `_old` и меняет `isChanged`. Для сохранения такой объект передают по контракту операции целиком.

После снимка выполни несколько разных изменений:

```js
this.set('employee.lastname', 'Соколова');
this.set('contacts.0.contact', 'anna.work@example.test');
this.push('contacts', { contact_type: 2, contact: 'anna.home@example.test' });
```

Правка фамилии относится к `obEmployee`. Старый контакт попадёт в `contacts._mutations.upd`, новый — в `add`. Несколько правок одного нового контакта остаются одной операцией добавления. Если добавить контакт и удалить его до сохранения, эта новая запись исчезнет из `add` и не потребует удаления на сервере.

Журнал содержит ссылки на строки. Не используй его как архив изменений или независимую копию. При необходимости сохранить конкретное состояние запроса сделай отдельный DTO.

## touch: изменение вложенных данных

Если наблюдатель получает массив сотрудников с вложенными контактами, изменение контакта должно дойти до обоих уровней:

```js
this.$.obEmployees.snapshot();
this.set('employees.0.contacts.0.contact', 'anna.work@example.test');

// Изменён контакт внутри первого сотрудника.
this.employees[0].contacts._mutations.upd[0]
  === this.employees[0].contacts[0]; // true

// Сотрудник затронут через contacts, его собственные поля не изменялись.
this.employees._mutations.touch[0] === this.employees[0]; // true
this.employees._mutations.upd.length; // 0
```

Здесь `obEmployees.data` связан с `employees`; снимок сделан после загрузки. `touch` нужен, чтобы при обходе изменений дойти до журнала контактов. Он не означает, что нужно сохранить все поля сотрудника, и не заменяет `contacts._mutations`.

При отдельном наблюдателе над `contacts` родительский `touch` не нужен: корень наблюдения уже совпадает с коллекцией, которую сохраняет команда. Выбор границы наблюдения и способа передачи изменений разобран в [сохранении части формы](/nfjs/partial-save) и [вложенных данных](/nfjs/nested-changes).

`touch` формируется автоматически; метода `touch()` нет. Если после вложенной правки изменить ещё и поле самого родителя, он может присутствовать одновременно в `upd` и `touch`.

## Уведомления через несколько уровней

Каждая связь по пути редактирования должна возвращать уведомление родителю:

```html
<pl-form-level3.employee.contacts contacts="{{contacts}}"></pl-form-level3.employee.contacts>
```

Внутри субформы:

```html
<template d:repeat="{{contacts}}" d:as="contact">
  <pl-input label="Контакт" value="{{contact.contact}}"></pl-input>
</template>
```

Цепочка получается такой: `pl-input` → контекст строки → субформа → родитель → `pl-data-observer`. Если поставить `[[contacts]]` на редактируемый повтор или границу субформы, общего объекта в памяти недостаточно: уведомление об изменении может не дойти до наблюдателя.

Из обработчиков меняй данные методами `set`, `push`, `splice`. Прямое `this.contacts[0].contact = value` не уведомляет Polylib.

## Принять изменения, сбросить признаки, отменить ввод

| Действие | Что происходит |
| --- | --- |
| `snapshot()` | Текущие значения становятся исходными, журналы очищаются, `isChanged` сбрасывается |
| `reset()` | Журналы и `isChanged` очищаются; значения и прежний `_old` сохраняются |
| Отмена редактирования | Форма восстанавливает сохранённую копию или перечитывает данные, затем делает снимок |

`reset()` не является отменой. После следующего уведомления старые отличия от `_old` могут снова включить `isChanged`.

Для локальной отмены храни копию модели отдельно от наблюдаемого объекта. Пример для JSON-модели контактов с датами в виде строк:

```js
rememberContacts() {
  this._savedContacts = JSON.parse(JSON.stringify(this.contacts, (key, value) =>
    key.startsWith('_') ? undefined : value
  ));
}

cancelContactChanges() {
  const restored = JSON.parse(JSON.stringify(this._savedContacts));
  this.splice('contacts', 0, this.contacts.length, ...restored);
  this.$.obContacts.snapshot();
}
```

Вызывай `rememberContacts()` после загрузки и после успешного сохранения. JSON-копирование в этом примере соответствует JSON-модели; для объектов `Date` или других типов нужен способ копирования, сохраняющий эти типы.

## Почему нельзя принять только поддерево общего наблюдателя

`snapshot(object)` делает снимок переданного поддерева, но одновременно сбрасывает **общий** `isChanged` этого наблюдателя. Маркеры массивов выше поддерева при этом могут остаться. Метод не вычисляет корректный общий признак оставшихся несохранённых правок.

Ещё одна особенность: `_old` и `_mutations` хранятся в самих данных. Два наблюдателя над одним объектом или пересекающимися ветками используют общие служебные поля. Они не создают независимых снимков.

Для независимого сохранения выдели непересекающиеся части данных и отдельного наблюдателя на каждую. Родитель получает от них булевы признаки и объединяет их. Это разобрано в [сохранении части формы](/nfjs/partial-save).

## Данные и журнал изменений

Слева редактируются записи, рядом показаны JSON данных и журнал изменений. На исходных данных нажми «Показать touch»: название пункта первой записи изменится, сама запись появится в `touch`, а её пункт — в `upd` вложенного журнала.

Затем измени название самой записи, добавь новую и удали её до принятия снимка. Следи за `add`, `upd`, `del`, `touch` и сравни «Принять изменения» со «Сбросить признаки».
