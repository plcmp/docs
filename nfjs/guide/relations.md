# Сотрудник и контакты

Сохранение карточки затрагивает две таблицы. Сотрудник может быть новым, а коллекция контактов одновременно содержать добавленные, изменённые и удалённые записи. Все эти изменения должны либо сохраниться вместе, либо откатиться вместе.

## Журнал дочерней коллекции

После загрузки `pl-data-observer` принимает снимок контактов. Затем добавление через `push`, удаление через `splice` и изменения полей через биндинги попадают в `contacts._mutations`.

```js
{
  add: [{ contact_type: 2, contact: 'anna@example.test' }],
  upd: [{ id: 12, employee_id: 1, contact_type: 1, contact: '+7 900 000-00-02' }],
  del: [{ id: 13, employee_id: 1, contact_type: 2, contact: 'old@example.test' }],
  touch: []
}
```

Добавленная запись пока не имеет серверного `id`. Удалённая уже отсутствует в видимом списке, но сохранена в `del` до принятия нового снимка. Добавление и последующее удаление одной новой записи не должно приводить к удалению строки из базы.

В этой карточке контакт не содержит собственных вложенных коллекций, поэтому основная работа идёт с `add`, `upd` и `del`. Значение `touch` нужно на следующем уровне вложенности: изменение потомка затрагивает родителя, даже когда его собственные поля не менялись. Подробный пример с JSON — в [снимках и изменениях](/nfjs/change-tracking).

## REST: одна операция приложения

Форма передаёт сотрудника и журнал контактов:

```js
await this.$.aSave.execute({
  employee: this.employee,
  contacts: this.contacts._mutations
});
```

На сервере одна операция выполняет последовательность:

1. Открывает соединение и начинает транзакцию.
2. Добавляет или изменяет сотрудника через broker.
3. Получает `id` сотрудника.
4. Удаляет, изменяет и добавляет контакты. Новым строкам назначает `employee_id` на сервере.
5. Выполняет `commit` и возвращает `{ data: { id } }`.

При исключении выполняется `rollback`; в `finally` соединение освобождается. Все вызовы используют **один `connect`**. Отдельный `dbapi.broker()` внутри этой последовательности получил бы собственное соединение и не участвовал бы в общей транзакции.

## serverEndpoints: корень и вложенные действия

У действия задан `paths="contacts"`. Оно отправляет корневые поля сотрудника и строки изменений контактов с `$action`; серверный обработчик разбирает их по именованным веткам.

<details class="docs-code">
<summary>Описание операции aSave</summary>

```js
serverEndpoints = {
  action: {
    aSave: {
      '@main': {
        type: 'broker', action: 'company.employee.mod', out: 'id'
      },
      contacts: {
        '@del': [{ type: 'broker', action: 'company.employee_contact.del',
          args: { '...': '*' } }],
        '@upd': [{ type: 'broker', action: 'company.employee_contact.upd',
          args: { '...': '*' } }],
        '@add': [{ type: 'broker', action: 'company.employee_contact.add',
          args: { '...': '*', employee_id: '/id' } }]
      }
    }
  }
}//serverEndpoints
```

</details>

| Элемент | Что происходит |
| --- | --- |
| `@main` | Сначала сохраняется сотрудник |
| `out: 'id'` | Полученный ключ становится доступен последующим веткам |
| `contacts` | Обрабатывается одноимённая дочерняя коллекция |
| `@add`, `@upd`, `@del` | Выбирается действие по изменению строки |
| `'...': '*'` | В аргументы копируются поля текущей строки |
| `employee_id: '/id'` | Ключ сотрудника берётся из корня операции и заменяет клиентское значение |

Операции используют одну транзакцию выбранного провайдера. Ошибка дочернего вызова отменяет уже выполненное изменение сотрудника. Если сценарий обращается к нескольким провайдерам, общей распределённой транзакции это не создаёт.

## Какой контракт выбрать

| Сценарий | REST | serverEndpoints |
| --- | --- | --- |
| Сотрудник и обычная дочерняя коллекция | Явные циклы по журналу | Декларативные ветки `@add`, `@upd`, `@del` |
| Дополнительные шаги и вычисления на JavaScript | Обработчик описывает порядок сам | Прикладную логику удобнее вынести в зарегистрированную операцию |
| Несколько уровней коллекций | Обработчик явно обходит нужные уровни | `paths` и вложенные ветки передают изменения по структуре данных |
| Сохранение одной области формы | Отдельный маршрут и журнал этой области | Отдельное действие и пути этой области |

## Проверь сохранение и откат

1. У существующего сотрудника добавь почту и измени телефон. Сохрани и открой карточку заново.
2. Удали почту, сохрани и убедись, что она не вернулась после перечитывания.
3. Повтори действия в другом варианте экрана: оба работают с теми же данными.
4. Для проверки транзакции вызови `/guide/employee/save` с изменённой фамилией и новым контактом, у которого `contact: null`. Ограничение `NOT NULL` должно отклонить контакт. Повторное чтение сотрудника должно вернуть прежнюю фамилию.
5. Повтори ошибочный вызов для `aSave` формы с `serverEndpoints`: результат отката должен совпасть.

Последняя проверка выполняется на учебных данных через HTTP-клиент, поскольку интерфейс блокирует отправку незаполненного обязательного поля. Подробности формата запросов — в [HTTP и контексте запроса](/nfjs/backend/http).

Не принимай общий снимок после сохранения только контактов, если поля сотрудника ещё изменены. Пример независимых областей — в [частичном сохранении](/nfjs/partial-save), вложенных `pl-action` — во [вложенных данных и paths](/nfjs/nested-changes).
