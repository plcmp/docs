# Разделы, операции и права

DBFW связывает прикладные данные с метаданными разделов. **Раздел** описывает сущность, **операция** — допустимое действие над ней. Backend вызывает операцию по коду через `dbapi.broker` или `connect.broker`, а DBFW выбирает способ исполнения и применяет контракт записи.

## Метаданные DBFW

| Объект | Назначение |
| --- | --- |
| `nfc.modulelist` | Группы прикладных разделов |
| `nfc.unitlist` | Разделы, их коды, подписи и параметры хранения |
| `nfc.unitbps` | Операции разделов и привязка к write-функциям |
| `nfc.role_unitprivs` | Права роли на видимость раздела |
| `nfc.role_unitbpprivs` | Права роли на выполнение операций |
| `nfc.userroles` | Назначение ролей пользователю в организации |
| `nfc.menuroles` | Видимость пунктов меню для роли |

Таблица PostgreSQL и раздел DBFW связаны, но это разные объекты. Создание таблицы само по себе не регистрирует broker-операции и не выдаёт пользователю права.

Метаданные разделов редактируются в «Инструменты разработчика → Модули и разделы» и сохраняются в `dbsrc/<schema>/dat/nfc.modulelist`. Права настраиваются в «Система → Роли».

## Раздел и его opt

Раздел `company.employee` по умолчанию работает с таблицей `company.employee`. Существенные настройки `opt`:

| Свойство | Назначение |
| --- | --- |
| `table` | Явное соответствие раздела схеме и таблице; при отсутствии они выводятся из кода раздела |
| `primaryKey` | Поле и тип ключа, например `id::bigint`; при отсутствии broker определяет ключ по метаданным таблицы |
| `idGenMethod` | Способ получения ключа: `self` — default таблицы, `main` — общая последовательность, `ext` — ключ задаётся извне |
| `divideType` | Деление данных по организации `org`, группе `grp` или общая область `sys` |

Для таблицы со своей последовательностью и общими данными достаточно соответствующих `idGenMethod: 'self'` и `divideType: 'sys'`. Доступность конкретной строки и разрешённые переходы состояния определяет контракт раздела.

## Стандартные действия

| Действие | Вход | Результат |
| --- | --- | --- |
| `add` | Поля новой записи | Объект с ключом созданной записи в `data` |
| `upd` | Ключ и изменяемые поля | Объект с ключом изменённой записи в `data` |
| `del` | Ключ записи | Объект с ключом удалённой записи в `data` |

```js
const result = await dbapi.broker('company.employee.upd',
  { id: employeeId, lastname: 'Волкова' }, { context });
```

Для стандартной табличной операции broker отбирает поля, которые существуют в таблице. Он формирует параметризованный SQL и вызывает `nfc.f_broker8exec`. Внутри той же транзакции выполняется `nfc.f_bp8before`, включая проверку права операции, затем запись и `nfc.f_bp8after`.

`use_privs: true` в `nfc.unitbps` включает проверку прав стандартного действия. Выключать её ради работоспособности формы не нужно: выдай нужное право роли.

## Псевдодействие mod

```js
await dbapi.broker('company.employee.mod', employee, { context });
```

Для раздела с обычным генерируемым ключом `mod` выбирает `add`, если ключ пуст, и `upd`, если ключ передан. Для `idGenMethod: 'ext'` broker проверяет существование записи с этим ключом. Регистрируются операции `add` и `upd`; отдельная запись unitbp `mod` для этого выбора не нужна.

`mod` не принимает массив ключей. При явном API создания или обновления удобнее вызывать соответствующее действие напрямую: это делает контракт операции однозначным.

## Своя write-функция

Поле `exec_function` у unitbp задаёт функцию PostgreSQL. Такой контракт нужен, когда запись включает несколько таблиц, проверку состояния или специальное правило, которое не выражается стандартным табличным действием.

| Поле unitbp | Пример |
| --- | --- |
| `code` | `company.employee.rename` |
| `caption` | `Изменить фамилию` |
| `exec_function` | `company.f4employee8rename` |
| `use_privs` | `true` |

Вызов backend остаётся задачей с понятными аргументами:

```js
const result = await dbapi.broker('company.employee.rename',
  { id: employeeId, lastname: 'Волкова' }, { context });
```

Ветка с `exec_function` вызывает функцию напрямую внутри соединения broker. **Проверку прав и правила записи должна выполнять сама write-функция.** Для штатной проверки операции используется `nfc.f_bp8before`; её нельзя заменять предварительной проверкой в HTTP-обработчике. `use_privs` само по себе не добавляет обёртку вокруг произвольной `exec_function`.

Аргументы функции `p_id` и `p_lastname` могут заполняться ключами `id` и `lastname`. Результат зависит от SQL-сигнатуры: функция, возвращающая набор строк, даёт массив в `result.data`. Зафиксируй форму ответа в своём API; не предполагай для любой функции табличный ответ `{ id }`.

## Чтение и UI-доступ

Право видеть пункт меню, право прочитать данные и право изменить запись проверяются на разных уровнях.

| Уровень | Что определяет |
| --- | --- |
| Меню | Доступность ссылки на экран |
| Представление или запрос чтения | Какие строки видит пользователь |
| `pl-access` | Какие действия интерфейс предлагает пользователю |
| Broker/write-функция | Допустима ли сама операция записи |

Скрытая кнопка не заменяет проверку записи на сервере. И обратное: наличие пункта меню не гарантирует видимость данных, если у роли нет права на раздел.

## Типовые причины ошибок

| Сообщение или симптом | Причина и действие |
| --- | --- |
| «Раздел … не найден» | Проверь код в `nfc.unitlist` и применение его исходников |
| «Действие … не найдено» | Зарегистрируй конкретный unitbp, который вызывает backend |
| Доступ запрещён | Проверь роль пользователя, организацию и право на операцию |
| Новая колонка не сохраняется | Проверь метаданные раздела и перезапуск процесса после изменения структуры: broker кеширует описание таблицы |
| Своя функция обходит проверку прав | Добавь проверку в write-контракт; регистрация `exec_function` не делает её автоматически |
| После удаления остаются дочерние записи | Определи их обработку в операции удаления; транспорт не задаёт каскадное поведение |
