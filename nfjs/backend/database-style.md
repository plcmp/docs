# Стиль объектов PostgreSQL

Имена базы данных должны быть читаемыми, предсказуемыми и пригодными для использования без двойных кавычек. В NFJS используются короткие английские `snake_case` имена, префиксы для типов объектов и общий формат связи между объектом и его параметрами.

## Идентификаторы и схемы

| Правило | Требование |
| --- | --- |
| Символы | Только строчные латинские буквы `a-z`, цифры `0-9` и подчёркивание. |
| Первый символ | Латинская буква `a-z`. |
| Длина | До 63 символов; используй запас для составных имён и суффиксов. |
| Зарезервированные слова | Не используй зарезервированные слова PostgreSQL. |
| Квалификация | В SQL обращайся к объекту как `schema.object`, например `core.param`. |
| Кавычки | При таком формате имён SQL-идентификаторы обычно не нужно заключать в кавычки. |

Имя должно объяснять роль объекта или поля. Для составных терминов используй `_`: `employee_contact`, `date_begin`, `created_at`. Сокращай имя только тогда, когда оно остаётся однозначным в предметной области.

## Таблицы и поля

Имя таблицы — короткое существительное в единственном числе. Подчинённую или расширяющую таблицу называй от имени родительской через `_`; справочники в предметной схеме можно начинать с `ref_`.

| Имя поля | Тип и назначение |
| --- | --- |
| `id` | `int8`, суррогатный первичный ключ. |
| `pid` | `int8`, ссылка на родительскую запись в составе дочерней сущности. |
| `hid` | `int8`, ссылка для иерархии. |
| `code` | Короткий код или аббревиатура, часто для справочника или интеграционного контракта. |
| `name`, `caption` | Краткое человекочитаемое название термина. |
| `description` | Полное описание термина или записи. |
| `note` | Дополнительное примечание. |
| `date_begin`, `date_end` | Границы периода без времени, тип `date`. |
| `datetime_begin`, `datetime_end` | Границы периода со временем, тип `timestamp` или `timestamptz` по контракту. |
| `time_begin`, `time_end` | Границы времени в течение суток, тип `time` или `timetz` по контракту. |
| `created_at`, `updated_at`, `deleted_at` | Временные отметки операций, обычно `timestamptz`. |
| `created_by`, `updated_by`, `deleted_by` | Идентификатор пользователя, выполнившего операцию. |
| `org`, `grp` | Идентификаторы организации или группы организаций, если область данных этого требует. |
| `user_id` | Ссылка на пользователя приложения. |

Описание таблицы и полей фиксируй в комментариях объектов. Описание расширяющей таблицы может дополнять название родительской сущности через двоеточие, например «Параметры : Возможные значения».

## Имена объектов

Префикс отделяет тип объекта. `4` связывает объект с таблицей, а `8` отделяет имя таблицы от целевого действия или назначения.

| Объект | Шаблон | Пример |
| --- | --- | --- |
| Основное представление | `v4<table>` | `v4param` |
| Дополнительное представление | `v4<table>8<purpose>` | `v4param8rep` |
| Функция | `f4<table>8<action>` | `f4param8add` |
| Триггер | `tr4<table>8<purpose>` | `tr4param8checks_before` |
| Последовательность | `s4<table>` | `s4param` |
| Первичный ключ | `pk4<table>` | `pk4param` |
| Уникальное ограничение | `uk4<table>8<purpose>` | `uk4param8code` |
| Внешний ключ | `fk4<table>8<field>` | `fk4param8datatype` |
| Проверочное ограничение | `ch4<table>8<purpose>` | `ch4param8trimcode` |
| Исключающее ограничение | `ex4<table>8<purpose>` | `ex4booking8dates` |
| Индекс | `i4<table>8<field-or-purpose>` | `i4param8dt` |

Главное уникальное ограничение может не иметь суффикса назначения. Для составного индекса указывай цель индекса, а не перечисляй в имени каждый столбец.

## Функции и триггеры

Параметры функций начинай с `p_`, локальные переменные — с `v_`. Суффикс функции отражает её действие:

- `add`, `upd`, `del` — запись для конкретного write-контракта;
- `checks` — проверки, принадлежащие DB write-функции;
- `tr` — тело триггера до или после изменения;
- `tr_checks` — проверка для триггера `checks_before`;
- `tr_deferred` — отложенное действие;
- `tr_deferred_checks` — отложенная проверка связанного набора данных.

У триггеров суффикс обозначает момент и назначение. `before` изменяет данные до записи; `checks_before` проверяет связанные строки; `after` вычисляет зависимые значения после записи; `deferred_after` и `deferred_checks_after` выполняются после того, как транзакция обработала связанные строки.

## Представления чтения и бизнес-запись

Основное представление `v4<table>` содержит поля своей таблицы и, при необходимости, человекочитаемые значения внешних ключей с составными именами вроде `country_id_caption`. Дополнительное представление используй для самостоятельной проекции с отдельным назначением.

Читай прикладные данные из `v4*` представлений параметризованным SQL, запрашивая нужные колонки. Например, в принятой модели `core.param` короткий запрос к основному модели чтения выбирает явно заданные поля и связывает код параметром:

```sql
select id, code, caption
  from core.v4param
 where code = :code
```

Представление строится от физических таблиц и справочников; не строй его через другое представление, включая другое `v4*`. Это сохраняет независимое создание объектов мигратором и понятные источники каждого поля.

В backend запись выполняется через зарегистрированное broker-действие `dbapi.broker(action, payload, { context })` или `connect.broker(action, payload)` в общей транзакции. Не заменяй broker-вызов `INSERT`, `UPDATE`, `DELETE` в JavaScript и не вызывай write-функцию напрямую через `query` или `func`.

## Ограничения, триггеры и сообщения

Выражай инвариант в базе данных в наиболее простом подходящем виде: `NOT NULL`, `FOREIGN KEY`, `UNIQUE`, `CHECK` или `EXCLUDE`. Например, ограничение формата кода в `core.param` можно объявить так:

```sql
alter table core.param
  add constraint ch4param8trimcode
  check (code = trim(code));
```

Используй триггер, когда правило требует нескольких связанных записей, отложенной проверки либо вычисления связанного состояния. Не дублируй DB-инвариант предварительным JS-запросом перед broker.

Для ограничений дай стабильные имена по таблице выше и человекочитаемые сообщения в `msgs.json` под `dbWarn`. PostgreSQL-провайдер сопоставляет SQLSTATE с именем ограничения и ищет локальный текст; если его нет, используется общий текст `dbWarnCommon`. Формат ключей и примеры см. в [ошибках backend](/nfjs/backend/errors).

Пример условной базы имён из рекомендаций редактора БД: схема `core`, таблица `param`, справочник `ref_datatype`, представление `v4param`, функция добавления `f4param8add`, уникальный ключ `uk4param8code`. Полный контракт создаваемого объекта и его комментарии важнее краткости имени.
