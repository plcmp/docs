# DB-исходники модулей

`@nfjs/migrate` сравнивает состояние PostgreSQL с файловыми исходниками модулей. `dbsrc` — версионируемое описание объектов схемы, миграций и начальных данных. Источник объекта хранится вместе с модулем-владельцем его схемы.

## Владение схемой

Каждая схема PostgreSQL должна иметь одного владельца в NFJS-пакетах. Для одного имени схемы держи `dbsrc/<schema>` в одном модуле. Это важно для экспорта объектов, определения владельца миграций и сборки источников данных.

Мигратор сначала получает перечень активных схем через `getSchemaModules(undefined, true)`, который сопоставляет схемы с загруженными extension modules. Затем `getAllObjFiles`, `getAllDatFiles`, `getAllMigrationFiles` и `getAllSysFiles` ищут файлы в `node_modules` по именам найденных схем.

У этого поиска есть существенная особенность: `modules.only` ограничивает активные модули при поиске владельцев, но последующий файловый обход фильтрует по имени схемы, а не по пакету-владельцу. Если два установленных пакета содержат `dbsrc/<одинаковая схема>`, в результат попадут объекты из обеих папок, даже когда один пакет выключен через `modules.only`. Не допускай повторного владения одной схемой и повторов DB-объектов в установленных модулях.

## Структура каталогов

```text
<module>/
  dbsrc/
    <schema>/
      src/
        table/
        sequence/
        view/
        function/
        trigger/
      dat/
        <table>/
          data.json
          eSch.json
          iSch.json
      mig/
        <YYYY-MM>/
          <migration-name>.sql
      sys.json
```

| Раздел | Содержимое и формат |
| --- | --- |
| `src/table/*.sql` | JSON-описания таблиц. Файл хранится с расширением `.sql`, но мигратор читает содержимое как JSON. |
| `src/sequence/*.sql` | JSON-описания последовательностей, также под расширением `.sql`. |
| `src/view/*.sql` | SQL определения представлений. |
| `src/function/*.sql` | SQL определения функций. |
| `src/trigger/*.sql` | SQL определения триггеров. |
| `dat/<table>/data.json` | Сериализованные данные, предназначенные для импорта в таблицу. |
| `dat/<table>/eSch.json` | Схема выгрузки данных из базы в `data.json`. |
| `dat/<table>/iSch.json` | Схема чтения `data.json` и подготовки SQL-команд импорта. |
| `mig/<YYYY-MM>/*.sql` | SQL-миграции, которые выполняются один раз и отмечаются в таблице истории мигратора. |
| `sys.json` | Список необходимых PostgreSQL extensions в массиве `extensions`. |

Объекты в `src` обнаруживаются по форме `dbsrc/<schema>/src/<type>/<name>.sql`. Текущие типы директории — `table`, `sequence`, `view`, `function`, `trigger`.

## Получение и сохранение исходников

`@nfjs/db-editor` позволяет создавать и редактировать объекты базы данных, сравнивать описания и видеть SQL изменений. Сохранение определения из базы в `dbsrc` выполняет инструмент `@nfjs/dev` «Подготовка исходников БД»; обзор редактора доступен в [редакторе БД](/nfjs/tools/db-editor), порядок экспорта — в [сохранении исходников](/nfjs/tools/db-editor?id=сохранение-исходников).

При сохранении выбранного DB-объекта `@nfjs/dev` запрашивает его описание у DBFW, преобразует таблицы и последовательности в JSON, а текстовые объекты сохраняет как SQL. `@nfjs/migrate/sourceFiles.saveObjToFile()` записывает файл в каталог владельца `dbsrc/<schema>/src/<type>/`. Миграция сохраняется в модуль, определённый по схеме в имени файла, внутри каталога месяца. Экспорт seed-данных проходит через схемы EI: `eSch.json` формирует `data.json`; `iSch.json` используется для подготовки импорта.

Имя каталога схемы и список объектов должны соответствовать владельцу предметной области. Создавай объектные исходники из установленной схемы через редактор/сохранение исходников или добавляй проверенные готовые источники в этот же каталог. Не оставляй состояние базы источником истины без синхронного DB-исходника.

## Схемы миграций и начальных данных

### Seed-данные

`data.json` описывает набор фиксированных данных, принадлежащий исходной схеме. `eSch.json` задаёт извлечение, `iSch.json` — импорт. Если один из файлов не найден в `dat/<table>`, сканер проверяет общий набор схем `@nfjs/migrate/data_schemas/<table>`; для общего `eSch` он добавляет фильтр схемы при экспорте.

Мигратор вычисляет хеш содержимого каждого `data.json` и повторно импортирует seed, когда хеш изменился. Отметки записываются в `public.nf_objects` для конкретного источника; изменение данных в файле — это сигнал к повторному импорту, поэтому seed используй для управляемых справочных и стартовых наборов.

### `sys.json`

В `sys.json` перечисляются расширения PostgreSQL, нужные объектам схемы, например операторным классам ограничений. Перед применением объектных изменений мигратор проверяет их наличие и при необходимости создаёт расширения через отдельное соединение с административными credentials. Этот шаг выполняется отдельно от основной транзакции обновления.

### Миграционные файлы

`NFMig.createName(schema, count, comment)` создаёт уникальное имя с датой, временем, миллисекундами, счётчиком, случайным идентификатором и кодом схемы. Внутри SQL-файла можно помечать блоки заголовками `--[block]` с JSON-полями `event` и `when`. Непомеченный SQL-блок тоже допустим; он исполняется после именованных событий.

```sql
--[block]{"event":"run","when":"before"}
-- DDL, которое должно предшествовать сравнению объектных описаний

--[block]{"event":"run","when":"after"}
-- DDL после применения объектных исходников и данных
```

Миграция запускается один раз: имя файла записывается в `public.nf_migrations` в той же основной транзакции, что и изменения схемы. При тестовом режиме эта отметка также откатывается. Не редактируй уже применённый файл, чтобы повторно запустить его: добавь новую миграцию с новым именем.

Именованные блоки распределяются по фазам обновления:

| Событие | Порядок и назначение |
| --- | --- |
| `run` / `before` | До сравнения объектных описаний; например, подготовительное переименование объекта. |
| `safedrop` / `after` | После необходимых безопасных удалений и до основного изменения таблиц. |
| `main` / `after` | После основных изменений таблиц. |
| `func`, `trig`, `view`, `pkey` / `after` | После создания функций, триггеров, представлений и ключей соответствующей фазы. |
| `dats` / `after` | После импорта seed-данных. |
| `end` / `after` | После отложенных ограничений и завершающих объектов. |
| `run` / `after` | После основных объектных фаз и миграционных блоков с явным событием. |

После именованных блоков мигратор выполняет оставшиеся блоки файла. Разделяй блоки по предметному смыслу и отмечай фазу только когда миграции нужен заданный порядок относительно сравнения объектов или seed-импорта.

## Конфигурация `@nfjs/migrate`

Модуль может выполнять проверку при запуске, если `doMigrate` включён. Для явного запуска при старте доступен параметр `--domigrate=true`. Соединение, провайдер и схема выбираются по активным модулям приложения; учётные данные проверки и применения миграций задаются в `@nfjs/migrate.data_providers.<provider.name>`.

| Свойство | Тип | Назначение |
| --- | --- | --- |
| `doMigrate` | boolean | Запускать миграционную проверку при старте модуля. |
| `doSilent` | boolean | Не задавать вопросы в терминале; использовать значения конфигурации и аргументов запуска. |
| `checkType` | строка: `simple` или `force` | `simple` использует сохранённые хеши источников; `force` повторно рассматривает все объектные и data-источники. |
| `defaultRunType` | строка: `r`, `t`, `v`, `f`, `m` | Режим применения для `doSilent`: выполнить, протестировать, вывести SQL, сохранить SQL в файл или пропустить. |
| `defaultDoUnsafeDrop` | boolean | Начальный ответ на применение разрушительных `unsafedrop` изменений. В silent-режиме `false` пропускает этот блок. |
| `onlySchemas` | массив строк | Ограничить обработку перечисленными именами схем. |
| `grantAllFunction` | строка или `false` | Функция назначения прав после обновления; по умолчанию `nfc.f_db8grant_all`. Значение `false` отключает вызов. |
| `data_providers.<name>.checkUserName` | строка | PostgreSQL-пользователь для проверки необходимости изменений. |
| `data_providers.<name>.checkUserPassword` | строка | Пароль пользователя проверки. |
| `data_providers.<name>.adminUserName` | строка | PostgreSQL-пользователь для выполнения обновления. |
| `data_providers.<name>.adminUserPassword` | строка | Пароль пользователя применения. |
| `data_providers.<name>.superUserName` | строка | PostgreSQL-пользователь для создания отсутствующих extensions. |
| `data_providers.<name>.superUserPassword` | строка | Пароль пользователя создания extensions. |

`name` в `data_providers.<name>` должен соответствовать имени провайдера и ключу конфигурации `@nfjs/migrate.data_providers`. Учётные данные проверки применяются к соединению проверки, административные — к транзакции изменения схемы, а superuser credentials используются только при необходимости установить перечисленные extensions.

Конфигурация для автоматического тестового запуска может выглядеть так:

<details class="docs-code">
<summary>Фрагмент config.json для тестового запуска</summary>

```json
{
  "@nfjs/migrate": {
    "doMigrate": true,
    "doSilent": true,
    "checkType": "force",
    "defaultRunType": "t",
    "defaultDoUnsafeDrop": false,
    "data_providers": {
      "default": {
        "checkUserName": "{{MIGRATE_CHECK_USER}}",
        "checkUserPassword": "{{MIGRATE_CHECK_PASSWORD}}",
        "adminUserName": "{{MIGRATE_ADMIN_USER}}",
        "adminUserPassword": "{{MIGRATE_ADMIN_PASSWORD}}",
        "superUserName": "{{DB_SUPERUSER}}",
        "superUserPassword": "{{DB_SUPERUSER_PASSWORD}}"
      }
    }
  }
}
```

</details>

Фрагмент включает проверку всех источников и тестовый прогон с откатом основной транзакции. Чтобы применять обновление, явно задай `defaultRunType: "r"` после проверки diff; `defaultDoUnsafeDrop` оставь `false`, пока разрушительные изменения не рассмотрены отдельно. Параметры запуска могут переопределять эти значения: например, `--migrate-run-type=t` задаёт тестовый режим, а `--migrate-only-schemas='sales;billing'` ограничивает список схем. Кавычки нужны shell, чтобы `;` осталась частью значения аргумента.

| `defaultRunType` | Поведение |
| --- | --- |
| `r` | Применить изменение и зафиксировать основную транзакцию. |
| `t` | Пройти применение, затем откатить основную транзакцию. Нужные системные extensions могут быть созданы ранее в отдельной транзакции. |
| `v` | Вывести собранный SQL в консоль без применения объектных изменений. |
| `f` | Записать SQL в `migrate_file.sql` в корне приложения без применения объектных изменений. |
| `m` | Пропустить применение. |

В интерактивном режиме модуль показывает выбор режима и спрашивает подтверждение `unsafedrop`, используя `defaultDoUnsafeDrop` как начальное значение. Поэтому `false` означает «не применять автоматически в silent-режиме» и начальный отрицательный выбор в интерактивном режиме; оператор может явно выбрать применение. Для деструктивного diff оставляй значение `false` по умолчанию и проверяй сгенерированный SQL до подтверждения.
